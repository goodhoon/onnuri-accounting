# 오클랜드 온누리교회 회계 — Day 1

실제 운영 앱을 위한 첫 구현입니다. Next.js App Router, Supabase Auth/PostgreSQL을 사용합니다. 현재 운영 중인 시스템이나 전체 회계 기능 완성본은 아닙니다.

## 구현된 범위

- 이메일·비밀번호 로그인, 로그아웃, 서버에서 검증하는 세션, 계정 승인 대기 화면
- 사용자 계정 활성화/비활성화, 역할 추가·제거, 마지막 활성 관리자 보호
- 교회 → 본부 → 분과 → 팀 조직 조회 및 관리자 조직명 변경
- 소속별 역할과 상위 조직에서 하위 조직으로 이어지는 권한 검사 함수
- 결재선 단계 이름 변경·추가·삭제·순서 변경, 마지막 지급 단계 유지
- 기본 결재선: 신청자 → 팀장 → 부서장 → 비전위원 → 지급 담당자
- 이전 결재선 버전 보존, 동시 수정 충돌 검출
- DB 변경 이력, 일반 사용자의 권한 상승 및 직접 쓰기 차단
- SQL 실행 기반 권한 테스트와 결재선 검증 테스트

신청자는 제출 주체이므로 결재선 편집 목록에는 승인·지급 단계만 저장합니다. 지출 건의 담당자 스냅샷과 실제 승인 행위는 Day 3~4에서 구현합니다.

## 시작하기

Node.js 22.13 이상(검증 환경: 24.22.1), npm이 필요합니다.

```sh
npm ci
cp .env.example .env.local
```

본인 소유의 Supabase 프로젝트에서 아래 순서로 진행합니다.

1. Authentication 설정에서 **새 사용자 공개 가입을 비활성화**합니다. 운영 계정은 관리자만 생성합니다.
2. SQL Editor에서 다음 파일을 순서대로 실행합니다. 신규 DB용 일회성 마이그레이션으로, 두 번 실행하지 않습니다.
   - `supabase/migrations/202611030001_foundation.sql`
   - `supabase/migrations/202611030002_initial_organization.sql`
   - `supabase/migrations/202611030003_admin_controls.sql`
3. Auth 사용자 관리에서 초기 관리자 계정을 생성하고, 확인된 이메일과 초기 비밀번호를 설정합니다. 기존 Auth 사용자가 있는 DB에는 자동 프로필 백필이 없으므로 새 프로젝트를 사용하거나 별도 이전 작업이 필요합니다.
4. `supabase/bootstrap-admin.sql`의 이메일 자리표시자를 본인의 계정으로 바꾸고 SQL Editor에서 실행합니다. 첫 관리자 생성에만 사용합니다.
5. `.env.local`에 프로젝트 URL과 **publishable key**를 설정합니다. `service_role`/secret key는 앱 코드나 `NEXT_PUBLIC_` 변수에 넣지 않습니다. 키·비밀번호를 대화창에 보낼 필요가 없습니다.
6. `npm run dev`를 실행하고 개발 서버 주소를 엽니다.
7. 관리자 로그인 후 사용자·권한에서 각 계정의 조직과 역할을 지정합니다. Supabase에서 만든 신규 계정은 기본적으로 비활성 상태입니다.

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
```

환경 변수가 없는 상태에서는 연결 준비 안내가 표시됩니다. 임시 관리자, 우회 로그인, 브라우저 저장소 기반 가상 사용자 기능을 제공하지 않습니다.

## 권한의 적용 범위

| 역할 | 적용 범위 |
|---|---|
| 관리자 | 전체 조직 설정·사용자 관리·결재선 관리·변경 이력 조회 |
| 신청자 | 지정한 조직. 지출 작성 권한은 Day 3에서 연결 |
| 팀장 / 부서장 / 비전위원 | 지정 조직과 그 하위 조직. 실제 승인 처리 권한은 Day 4에서 연결 |
| 지급 담당자 / 조회 담당자 | 지정한 조직 또는 명시적으로 선택한 전체 조직 |

활성 교회 구성원은 전체 **조직 명칭**과 결재선 템플릿을 조회할 수 있습니다. 다른 사용자의 프로필과 역할 전체는 관리자만 조회합니다. 재정 데이터 접근은 이후 예산·지출 테이블의 별도 RLS에 연결해야 합니다. 현재의 `has_org_role()` 함수만으로 미래 데이터가 자동 보호되는 것은 아닙니다.

일반 클라이언트에 테이블 직접 쓰기 권한을 주지 않습니다. 관리자 변경은 권한 검사와 이력 기록을 수행하는 RPC로만 허용됩니다. 프로필 생성 시 사용자 metadata의 `active`·`role` 값은 신뢰하지 않습니다.

## 조직도 반영 사항

- 제공된 「오클랜드 온누리교회 조직도 2026년 ver.0224」 사진 2장을 기준으로 37개 조직을 등록합니다.
- 세례팀·새벽팀·통역팀은 사진에서 상위 분과가 잘려 있어 이번 seed에서 제외했습니다.
- 조직도에 있는 개인 이름으로 로그인 계정이나 승인 권한을 자동 생성하지 않습니다.
- `COMMUNITY_01` 같은 코드는 이번 구현에서 부여한 **조직 식별 코드**입니다. 교회의 공식 회계코드가 아닙니다.
- 현재 조직 이름 변경만 화면에서 제공합니다. 조직 추가·이동·비활성화 화면, 회계연도·행사·예산 설정은 Day 2 범위입니다.

## 검증

```sh
npm test
npm run typecheck
npm run build
```

테스트는 PGlite의 실제 PostgreSQL 엔진에 migration을 적용하고 RLS/RPC를 실행합니다. Supabase 전용 `auth.users`, `auth.uid()`와 API 역할은 테스트에서 모사합니다. 따라서 운영 Supabase Auth의 이메일 전달, 세션 만료·갱신, 비밀번호 정책, 네트워크와 실제 PostgREST 동작까지 검증한 것은 아닙니다.

현재 결과와 제한은 `VERIFICATION.md`에 기록했습니다.

## 운영 배포 연결

원래 합의한 운영 구성은 GitHub → Vercel + Supabase입니다. Vercel에서는 이 폴더를 프로젝트 루트로 지정하고 동일한 두 환경 변수를 설정합니다. 인증 설정 변경은 Supabase 프로젝트에서 직접 수행합니다. 이 작업에서는 클라우드 계정 생성, 실제 데이터베이스 적용, 공개 배포를 수행하지 않았습니다. Day 1 소스 구현과 Day 7 운영 배포를 구분합니다.

운영 전에는 Auth 요청 제한, 비밀번호 정책과 MFA 적용 범위, 초기 관리자 인계, 세션 동작, 백업·복구, 회계 데이터 검증을 실제 환경에서 확인해야 합니다. 사용자 제거 전에는 계정을 비활성화하고 이력을 보존하는 방식으로 운영합니다.
